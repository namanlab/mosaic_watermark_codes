# MOSAIC: Set-Based Multi-Bit Watermarking for Language Models

MOSAIC is a multi-bit watermark for language-model text. It embeds a recoverable
`k`-bit payload (a user id, session token, timestamp, ...) into generated text so
that a party holding a secret key can read it back exactly, using only the
tokeniser, the key, and the prompt as context at detection time (no language
model).

MOSAIC reads the token stream as an **unordered multiset of parity samples**.
Each token, keyed by an order-canonical hash of its local context (the sorted
window of the previous `w` tokens), emits one parity check over a key-chosen
subset of the payload bits: a fountain (LT) code generated by the text itself.
The payload is recovered jointly from all collected checks by belief propagation.
Joint decoding removes the `β^k` exact-match ceiling of independent per-bit
decoders, inference uses only the multiset of checks, and extraction is
invariant to any rearrangement that preserves every sorted window, so block
reordering changes only the checks at block boundaries, and an edited token
corrupts at most `1 + w` checks.

This repository contains the MOSAIC implementation, the full experiment harness,
reimplementations of six multi-bit baselines (Cohen et al. in two variants)
evaluated under one shared protocol, and the analysis pipeline that regenerates every table, figure, and
quoted number of the paper.

```
   payload m (k bits)
        │  each generated token, keyed by an ORDER-CANONICAL hash of its
        │  local context (the SORTED previous-token window), commits to:
        ▼
   a random PARITY CHECK over the payload bits:  m[i] ⊕ m[j] ⊕ m[l]   (a fountain symbol)
        │  scramble by a keyed chip bit r, then bias the token toward
        ▼  green if the scrambled parity = 1, else red; sample as usual
   TEXT ──► detector recomputes every token's check from its context,
            reads its colour → a soft observation (LLR) of that parity,
            collects ALL of them (order irrelevant), and runs
            BELIEF PROPAGATION over the Tanner graph → recovers m + a p-value
```

### The MOSAIC source (`src/`)

- **`mosaic.py`**: `MosaicWatermark`, the top-level object. `generate()` embeds a
  payload during sampling (or produces an unmarked baseline with
  `watermark=False`); `detect_ids()` / `detect_text()` recover the payload and a
  p-value without a model; `perplexity()` scores text; `reconfigure()` changes
  payload size, bias, or window in place so one loaded model serves many
  settings. The bias is added to the logits first, then temperature and nucleus
  (top-p) truncation are applied to the biased distribution.
- **`content_prf.py`**: `ContentPRF`, the order-canonical keyed PRF. Every
  per-token quantity (green mask `G_t`, chip `r_t`, check subset `D_t`) is keyed
  on the **sorted multiset** of the preceding `w` tokens. Two positions with the
  same sorted window emit the same check, so the collected checks form a
  multiset.
- **`fountain_bp.py`**: the coding core: `robust_soliton()` for the check-degree
  distribution and `bp_decode()`, a belief-propagation decoder over the
  bipartite (payload bit, check) Tanner graph. Pure NumPy.
- **`conv_code.py`**: a rate-1/2 convolutional code with Viterbi decoding from an
  earlier sequential design, kept for reference; MOSAIC uses `fountain_bp.py`.

## Installation

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

Requirements: `torch`, `transformers`, `accelerate`, `numpy`, `pyarrow`,
`matplotlib`, `sentencepiece`, `protobuf`, `mauve-text`. A CUDA GPU is
recommended for Llama-2-7B (about 16 GB of GPU memory in fp16). The analysis
pipeline (`results/`) needs R with `jsonlite`, `ggplot2`, `scales`, `dplyr`, and
`tidyr`, plus Python with `numpy` and `transformers` (tokeniser only); it runs on
a laptop and loads no language model.

Gated models require a Hugging Face token with access to
`meta-llama/Llama-2-7b-hf` and (for the perplexity oracle)
`meta-llama/Llama-3.1-8B-Instruct`:

```bash
export HF_TOKEN=hf_xxx        # or: huggingface-cli login
```

## Data

**OpenGen prompts.** `data/opengen_data.parquet` is the OpenGen prompt set (from
the DIPPER paper, Krishna et al. 2023). It has a `prefix` column (the prompt) and
a `targets` column (the human continuation, used as the MAUVE reference). Prompts
are truncated to 128 tokens with the model's own tokeniser before generation.

**Token frequencies for the Qu et al. baseline (download separately).** Qu et
al.'s method assigns tokens to segments with a balanced map built from token
frequencies that the authors distribute in their data release. The file is not
included here: Qu et al.'s release is under a CC BY-NC 4.0 licence, while this
repository is MIT-licensed, so it is obtained from the authors:

1. Download `data_share.zip` from the "Download data" link in the README of
   [github.com/randomizedtree/segment-watermark](https://github.com/randomizedtree/segment-watermark).
2. Unzip it and copy `token_freq_llama.pkl` to `data/qu/token_freq_llama.pkl`.

`data/qu/` is listed in `.gitignore`. The Llama file serves Llama-2-7B, which
shares the Llama tokeniser. On first use, `src_baselines/qu_balance.py` builds
the balanced map for each segment count and caches it as
`data/qu/map_p<n>_key<key>.npy` (a few seconds each). Without the frequency file,
the Qu baseline stops with a message pointing here; every other method runs
without it.

## Quick start (the MOSAIC API)

```python
from src.mosaic import MosaicWatermark

# embed a 32-bit payload
wm  = MosaicWatermark(model_name="gpt2", secret_key="key", k_bits=32,
                      delta=6.0, gamma=0.5, temperature=0.8, top_p=0.95, window=2)
msg = [1,0,1,1,0,0,1,0]*4
res = wm.generate("The future of renewable energy", msg, max_new_tokens=200)

# detect (no model: tokeniser, key, and the prompt as context)
det = wm.detect_text(res["generated_text"], prompt="The future of renewable energy")
print(det["message"] == msg, det["p_value"])

# detect straight from token ids
det = wm.detect_ids(res["generated_ids"], prompt_ids=res["prompt_ids"])

# perplexity of watermarked vs unmarked text (quality)
plain = wm.generate("The future of renewable energy", msg, watermark=False)
print(wm.perplexity("The future of renewable energy", plain["generated_ids"]))
print(wm.perplexity("The future of renewable energy", res["generated_ids"]))

# reuse one loaded model across payload sizes / bias values (no reload)
wm.reconfigure(k_bits=48, delta=5.0)
```

Key parameters: `delta` (green-list logit bias, default 6), `gamma` (green
fraction, 0.5), `temperature` / `top_p` (nucleus sampling, 0.8 / 0.95), `window`
(context window `w`, 2), `soft_mag` (detector LLR magnitude `A`; the experiments
use 4). The prompt completes the windows of the first `w` generated tokens; when
it is unavailable, those `w` checks are lost and the rest decode as usual.

## Reproducing the experiments

See [`REPRODUCE.md`](REPRODUCE.md) for the step-by-step walkthrough. In brief:

### MOSAIC (`run_experiments_full.py`)

The harness is split into stages selected by `--experiment`; each loads at most
one heavy model at a time, writes or merges JSON into `results/`, checkpoints,
and resumes from its own output.

| `--experiment` | what it does | model(s) |
|---|---|---|
| `generate` | prompts + watermark; saves ids, marked/plain text, per-prompt match | generation model |
| `quality` / `quality-perplexity` | base-model perplexity (Llama-3.1 oracle) + MAUVE | oracle + gpt2-large |
| `robust-substitution` / `robust-insertion` / `robust-deletion` / `robust-reordering` | one token-level attack each (model-free) | none |
| `robust-paraphrase` | DIPPER paraphrase attack (generates paraphrases, then detects) | DIPPER |
| `robust` | runs all attacks; results merge into one file | DIPPER |
| `sweep-delta` | match rate + perplexity against the bias delta | gen + oracle |
| `sweep-tokens` | payload size x token budget match-rate heatmap | gen model |
| `sweep` | runs both sweeps | gen + oracle |

```bash
# full run on Llama-2-7B (stage 1 first; the rest depend on it)
python run_experiments_full.py --experiment generate --model meta-llama/Llama-2-7b-hf
python run_experiments_full.py --experiment quality  --model meta-llama/Llama-2-7b-hf
SUBSET_FRAC=0.1 python run_experiments_full.py --experiment robust --model meta-llama/Llama-2-7b-hf
SUBSET_FRAC=0.1 python run_experiments_full.py --experiment sweep  --model meta-llama/Llama-2-7b-hf

# fast smoke test on GPT-2 (3 prompts, small oracle/paraphraser)
MOSAIC_QUICK=1 python run_experiments_full.py --experiment generate --model gpt2
```

Environment knobs: `MAIN_MAX_PROMPTS` (0 = all prompts, else the first N in
order), `SUBSET_FRAC` (fraction of prompts for robustness and sweeps; default
0.15, the paper uses 0.1, i.e. 772 prompts), `ORACLE_MODEL`, `PARAPHRASE_MODEL`,
`PARAPHRASE_TOK`, `QUANTIZE_8BIT`, `CHECKPOINT_EVERY`, `LOG_EVERY`, and
`MOSAIC_QUICK=1` for the smoke test.

Fixed protocol: 200 generated tokens, delta = 6, gamma = 0.5, window = 2, nucleus
sampling (tau = 0.8, top-p = 0.95), payloads 16 / 20 / 24 / 32 / 48 bits, one
fixed seed, and each payload a fixed pseudorandom function of the prompt index
and the payload size, shared by MOSAIC and every baseline.

### Baselines (`run_baseline_experiments.py`)

Runs the baselines under the same protocol (same prompts, model, sampling,
bias, payload sizes, and per-prompt payloads), with model-free detection from the
generated token ids. The paper uses the first 1,000 OpenGen prompts:

```bash
MAIN_MAX_PROMPTS=1000 python run_baseline_experiments.py --method all --model meta-llama/Llama-2-7b-hf
MAIN_MAX_PROMPTS=1000 python run_baseline_experiments.py --method qu  --model meta-llama/Llama-2-7b-hf
MOSAIC_QUICK=1 python run_baseline_experiments.py --method all --model gpt2   # smoke test
```

`--method` is one of `mpac`, `qu`, `cyclic`, `wang`, `cohen`, `cohen_adapted`,
`janas`, or `all`.
Each run writes `results/opengen_baseline_<method>_<model>.json` and resumes from
it when interrupted, so remove an older file of the same name before switching
implementations. The analysis reads baseline results from
`results/other_models/`; move the files there after a run. The `config` block of
each file records which implementation produced it.

### Output format

Each result file is `results/<name>_<model>.json` with:

```json
{
  "config":    {"model": "...", "delta": 6, "gamma": 0.5, "temperature": 0.8,
                "top_p": 0.95, "tokens": 200, "watermark_sizes": [16,20,24,32,48], "...": "..."},
  "aggregate": [{"k": 16, "match_rate": 98.7, "bit_accuracy": 99.5, "median_p_value": 2.7e-37, "n": 7711}],
  "samples":   [{"prompt_index": 0, "k": 16, "message": [], "decoded": [],
                 "match": true, "bit_accuracy": 1.0, "generated_ids": []}]
}
```

### Tables, figures, and quoted numbers

With the result JSONs in `results/` and `results/other_models/`, one command
regenerates everything the paper reports:

```bash
Rscript results/make_paper_assets.R
```

It writes `paper/tables/*.tex`, `paper/figures/*.pdf`, and
`paper/tables/numbers.tex`, which defines every number quoted in the text (the
paper cites them as `\val{key}`). Heavier steps run as Python helpers, each
called only when its output is missing or older than its inputs, with outputs in
`results/derived/`:

| helper | output | what it computes |
|---|---|---|
| `compute_match_ci.py` | `main_bootstrap_ci.json` | 95% bootstrap CI of the match rate over prompts |
| `summarise_sweeps.py` | `sweep_delta_summary.csv`, `sweep_tokens_records.csv` | compact sweep summaries |
| `sample_diagnostics.py` | `mosaic_sample_diagnostics.csv`, `baseline_sample_repetition.csv`, `common_sample.json` | per-sample repetition and channel diagnostics; match rates on the shared prompts with CIs and McNemar tests |
| `robustness_comparison.py` | `robustness_comparison.csv` | every method under the same substitution, insertion, deletion, and reordering attacks; recomputes only methods whose result files changed |
| `dedup_decoding.py` | `mosaic_dedup_decoding.csv` | MOSAIC decoding with each repeated (window, token) observation counted once |

All helpers run in a single process, stream the large result files one sample
at a time (`stream_samples.py`), and load no language model, so the pipeline
fits a laptop: the R step peaks near 0.3 GB and the helpers near 0.4 GB. The
robustness comparison is the longest step (a few hours on one core for all
methods; minutes when one baseline changes).

## The baselines

All run on the shared green-list layer (`src_baselines/common.py`) with the same
sampling, and differ in how a payload is written onto it and read back.
"Extraction" is the decoding cost as a function of payload size `k`.

| Method (`--method`) | Paper | Mechanism | Extraction | Payload sizes |
|---|---|---|---|---|
| `mpac` | Yoo et al., NAACL 2024 | each token allocated to one payload bit by a hash of the previous token; majority vote per bit | O(T) | 16-48 |
| `qu` | Qu et al., USENIX Security 2025 | released RSBH method: balanced map from the previous token to a segment, Reed-Solomon [n, k] over GF(2^m), symbol value encoded by rolling the green list, argmax per segment then RS decoding | O(T 2^m) | 16-48 |
| `cyclic` | Fernandez et al., WIFS 2023 | message shifts a per-message green list; score all candidate messages | O(T 2^k) | 16-24 (paper: 16, 20) |
| `wang` | Wang et al., ICLR 2024 | whole message hashes the vocabulary partition; score all candidate messages | O(T 2^k) | 16-24 (paper: 16, 20) |
| `cohen` | Cohen et al., IEEE S&P 2025 | Figure 2: a fresh random bit per 21-token block, 2L zero-bit keys, both keys of every bit detected over the whole text | O(T L) | 16-48 |
| `cohen_adapted` | Cohen et al., IEEE S&P 2025, adapted | one-token blocks; a keyed schedule assigns each position to a bit, the detector knows it and decodes each bit by which of its two keys has more green tokens | O(T) | 16-48 |
| `janas` | Janas et al., 2025 | payload = a line over GF(2^{k/2}); one point per block of consecutive positions, recovered by Maximum Collinear Points | O(N^2) | 16-48 |

Notes on fidelity, documented in each source file:

- **Qu et al.** (`qu_segment.py`, `qu_balance.py`, `reed_solomon.py`) follows the
  method the paper evaluates, `rsbh` in the authors' release
  (github.com/randomizedtree/segment-watermark): 'hash' seeding with a one-token
  context and their salt 35317; green lists from `torch.randperm` seeded per
  context; the segment of a token given by the balanced map of the previous
  token, reproduced exactly from their `balance_hash/` procedure; the symbol
  value written by rolling the green list; Reed-Solomon codes chosen by their
  `rs_search.py` rule, (n, k, m) = (6, 4, 4), (6, 4, 5), (5, 3, 8), (6, 4, 8),
  and (10, 6, 8) for 16, 20, 24, 32, and 48 bits; detection from the third
  continuation token with argmax per segment and RS decoding, falling back to the
  first k symbols; and their newline rule during generation. The Reed-Solomon
  layer is implemented here for GF(2^m) and corrects the same number of symbol
  errors as their library.
- **Cohen et al.** (`cohen.py`) has no released implementation; the file
  implements their Figure 2 construction exactly on the shared green-list layer.
  The two choices the construction leaves to the zero-bit primitive are fixed by
  rule: blocks of 21 tokens (the smallest block whose expected z-score alone
  reaches the threshold at the measured flip rate) and detection when any window
  of 21 tokens reaches z >= 4. Undecided bits are reported as -1. A 200-token
  text holds at most 10 blocks, fewer than the 16 or more payload bits, so its
  match rate is zero at these payload sizes. The paper reports it in an appendix
  section.
- **Cohen et al., adapted** (`cohen_adapted.py`) is the variant of the earlier
  runs and the instantiation in the paper's tables and figures. It keeps the two keys per bit
  and the bit read off by which key carries the mark, and replaces the fresh
  per-block randomness with a keyed position-to-bit schedule that the detector
  shares, so each bit is decided from its own tokens. The schedule is indexed
  by position, so insertion and deletion shift every later token onto the
  wrong bit. Its PRF domain strings (`cohen.greenlist`, `cohen.alloc`) are those
  of the earlier runs, so it re-detects their stored texts exactly. The paper's
  file `opengen_baseline_cohen_adapted_<model>.json` is the earlier run's output
  under the new name; its `config.method` reads `cohen` because it predates the
  variant's name.
- **Janas et al.** places one point per block of consecutive positions, as in
  their construction, so insertion and deletion shift every later block.

`cyclic` and `wang` decode by scanning all `2^k` candidate messages, which is
exponential in the payload; the paper runs them at 16 and 20 bits.
